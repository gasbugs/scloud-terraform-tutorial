# 강사용 콘텐츠·녹화 구성안 · SAT와 AI 학습 운영

**제작안: 20분 영상 7편.** 이 문서는 시범 녹화 전 구성안이며 실제 20분 분량이 검증된 완성 대본은 아니다. 설명을 반복해 시간을 채우지 않는다. 각 5분 구간에는 새로운 개념 또는 실제 화면 증거가 있어야 한다. 토의·발표·시청자 응답 대기는 영상에 넣지 않는다.

로컬 사이트는 SCP 화면을 참고한 교육용 구현이다. Job 결과는 보존된 AWS G6 실행 기록이며 SAT 실행 결과로 소개하지 않는다. 저장된 생성 폼은 SCP 백엔드에 연결되지 않는다.

## 1차수 · AI 학습 전체 흐름과 SAT의 위치

**목표:** 데이터 수집·분할·학습·검증·모델 저장·활용의 전체 흐름에서 SAT Job이 맡는 구간과 사용자의 책임을 설명한다. GPU VM 직접 운영과의 차이는 다루되 AWS 서비스 선택은 7차수로 넘긴다. **자료:** 상품설명회 전사 00:09–03:20, 06:17–07:16.

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | 제목과 데이터+이미지+명령→GPU Job→모델·로그 흐름도를 표시한다. “학습은 모델 가중치를 갱신하는 코드의 실행입니다. VM에 로그인하면 사용자가 GPU 드라이버와 컨테이너 실행 환경까지 챙깁니다. SAT에서는 실행에 필요한 내용을 Job으로 제출하고 플랫폼이 자원 배치와 실행 흐름을 맡습니다.” 각 화살표를 가리키며 데이터 오류와 자원 오류가 서로 다르다는 사례를 설명한다. |
| 05:00–10:00 | 저장소와 컨테이너를 구분한 도식을 순서대로 강조한다. “원본 파일은 사용자 스토리지에 있고, Job은 지정한 스토리지를 연결해 컨테이너 내부에서 읽습니다. 이미지에는 코드와 런타임이 있고 Command가 시작점을 정합니다. 실행 후 지표와 모델 파일이 출력 위치에 남습니다.” 상품설명회에서 말한 GPU 클러스터 흐름을 화면의 네 단계에 대응시킨다. |
| 10:00–15:00 | 책임 분담 표를 확대한다. “플랫폼이 자원을 마련해도 데이터 형식, 코드의 파일 경로, 라이브러리 호환성은 사용자가 검증해야 합니다. 예를 들어 잘못된 파일 경로는 GPU를 늘려도 고쳐지지 않습니다. 반대로 준비된 코드라도 자원 할당량이 부족하면 실행 시작 자체가 지연될 수 있습니다.” 두 오류의 관찰 지점을 하나씩 짚는다. |
| 15:00–20:00 | 로컬 Job 목록을 열고 이름·상태·생성 시각·상세 링크만 보여 준다. “Job은 실행 요청을 식별하는 단위입니다. 목록의 완료 표시는 코드가 종료됐다는 뜻이고 성능은 뒤에서 별도로 확인합니다. 여기 보이는 것은 AWS G6 결과를 가져온 교육 기록입니다.” 2차수에서 원본 demo의 입력과 출력 경로를 추적한다는 연결로 마친다. |

### 1차수 보충 내레이션: Job 바깥의 AI 학습 흐름

0–5분의 흐름도를 확장해 원본 데이터를 수집하고 정제한 다음 train, validation, test로 나누는 장면을 보여 준다. “GPU가 투입되는 시점 이전에 데이터의 의미와 평가 방법을 정해야 합니다. 학습용 데이터에 test 정답이 섞이면 뒤에서 점수가 높아져도 신뢰할 수 없습니다. 이미지 분류에서는 픽셀과 레이블, 텍스트 분류에서는 문장과 레이블의 짝이 학습 입력입니다.” 이 설명은 SAT가 데이터 정제를 자동으로 수행한다는 뜻이 아니다.

5–10분에는 두 개의 화살표를 더한다. 첫째는 준비된 데이터·코드가 Job에 들어가는 화살표이고, 둘째는 모델 파일과 지표가 다시 사용자 스토리지로 나오는 화살표다. “Job은 학습 전체 생애주기의 한 실행 단위입니다. 데이터 수집 정책, 개인정보 처리, 모델을 서비스에 올릴지 여부는 별도 설계입니다. SAT를 사용해도 무엇을 학습시킬지와 결과를 어떻게 검증할지 결정해야 합니다.” 원본 demo의 입력과 출력은 다음 편에서 구체적으로 추적한다고 연결한다.

10–15분에는 실험을 재현하는 데 필요한 다섯 값을 표시한다: 데이터 버전, 코드·이미지 버전, 하이퍼파라미터, 난수 seed, 평가 방법. “동일한 Job 이름만으로 동일한 실험은 아닙니다. 모델이 개선됐다고 주장하려면 비교 대상이 같은 데이터 분할과 지표를 사용했는지 확인해야 합니다.” 여기서는 값의 개념만 설명하고 실제 파일의 숫자는 7차수로 남긴다.

15–20분에는 학습 후 단계도 보여 준다. “결과 파일을 저장한 뒤에는 모델을 재로딩하고, 입력을 전처리하며, 추론 품질과 운영 비용을 검토해야 합니다. Training Job의 Completed는 이 전체 절차의 끝이 아닙니다.” 로컬 Job 목록에서 이 차이를 다시 확인한다. 로컬 사이트가 제공하는 기록의 범위와 실제 SCP SAT가 관리하는 범위를 분명히 나눈다.

## 2차수 · 입력·출력 경로 매핑

**목표:** 저장소 원본, 컨테이너 마운트, Command, 결과 위치를 구분한다. 모델 성능과 로그 판독은 다루지 않는다. **자료:** 원본 demo 입력과 출력.

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | [입력 준비](http://127.0.0.1:8080/local#assets)를 열어 파일 종류, 준비 상태, 검증 표시를 차례로 가리킨다. “학습 시작 전에는 데이터와 모델 파일의 존재 및 무결성을 확인합니다. 파일 수가 맞아도 내용이 다르면 기대한 학습이 아닙니다.” 화면의 현재 값을 읽되 녹화 전 확인한 값만 말한다. |
| 05:00–10:00 | [원본 demo 상세](http://127.0.0.1:8080/local#jobs/b669419947d55d6991620cdf9bbcaa1f/details)의 이미지 URL, Command, 마운트 필드를 확대한다. “이미지는 실행 환경, Command는 실행할 프로그램, Mount Path는 프로그램이 입력을 보는 내부 위치입니다. 스토리지의 원래 URI와 내부 디렉터리는 같은 값일 필요가 없습니다.” 화면 값으로 원본→내부 경로의 한 줄을 직접 완성한다. |
| 10:00–15:00 | 파일 흐름도에서 입력 파일을 따라 코드가 읽는 위치까지 이동한다. “Command가 train.py를 호출해도 그 파일이 이미지 안에 없다면 시작에 실패합니다. 입력 마운트가 다른 경로면 파일을 찾지 못합니다. 출력 디렉터리를 준비하지 않으면 학습이 끝나도 결과가 기대 위치에 남지 않을 수 있습니다.” 각 실패가 생기는 위치를 커서로 표시한다. |
| 15:00–20:00 | 원본 demo 결과 파일 탭에서 실제 있는 파일과 링크만 보여 준다. 모델 가중치, 지표, 로그의 파일 역할을 구분하고, 없는 파일은 없는 것으로 표시한다. “경로 검증의 끝은 결과 파일이 접근 가능한가입니다. 파일의 성능 해석은 6차수에서 합니다.” 원본 스토리지·내부 입력·명령·출력의 네 칸을 화면으로 다시 연결한다. |

### 2차수: 원본 demo의 실제 입력·출력 지도

00:00–05:00의 입력 준비 장면에서 input-manifest.json을 열어 데이터 원천 bitext/Bitext-customer-support-llm-chatbot-training-dataset과 모델 원천 google/gemma-4-E2B-it를 가리킨다. train 2,700건, validation 540건, test 540건과 seed 42를 읽고, 이 숫자는 입력 번들의 구성이지 이번 짧은 실행에서 모두 평가했다는 의미는 아니라고 설명한다. 원본 demo의 run-config.json에는 eval_samples 20과 max_steps 10이 기록돼 있다.

05:00–10:00에는 run-config.json의 input_uri와 output_uri가 서로 다른 위치임을 보여 준다. 경로 전체를 외우게 하지 말고 inputs/v1과 runs/실행 ID라는 구조를 강조한다. 원본 파일을 내려받는 단계와 컨테이너가 보는 /work를 분리해 그린다. AWS S3 URI는 이 보존 실행의 위치이며 SCP Object Storage가 실제 같은 URI를 쓴다고 말하지 않는다.

10:00–15:00에는 입력 매니페스트의 dataset/train.jsonl과 model/model.safetensors를 나란히 놓는다. 첫 파일은 학습 예시, 둘째는 시작 모델 가중치다. 코드는 입력 위치를 정확히 읽어야 한다. Command와 이미지의 역할은 3차수 생성 폼에서 자세히 다루므로 여기서는 경로 흐름만 확인한다.

15:00–20:00에는 결과 폴더의 adapter/adapter_model.safetensors, checkpoints/checkpoint-10/trainer_state.json, metrics/baseline.json과 metrics/finetuned.json을 한 번씩 보여 준다. “모델 어댑터, 중간 학습 상태, 평가 지표는 서로 다른 출력입니다. 실제로 무엇이 개선됐는지는 6차수에서 수치를 비교합니다.” 출력 업로드 완료 로그를 마지막에 연결한다.

| 10:00–15:00 | 이미지 URL, 레지스트리 인증, Command, Volume/Object Storage 필드를 보여 준다. “이미지 안의 코드 경로, Command, 마운트 위치가 한 세트로 맞아야 합니다. 사설 레지스트리라면 접근 권한도 필요합니다.” 2차수의 원본 demo 경로를 이 폼의 해당 필드에 대응시키되 실제 Job을 제출한 것으로 말하지 않는다. |
| 15:00–20:00 | 요약 영역을 위에서 아래로 읽으며 이름·학습 형태·리소스·이미지·명령·스토리지·출력 위치를 대조한다. “요약은 실행 전에 불일치를 찾는 마지막 화면입니다. 데이터 경로가 틀리면 Command와 함께, GPU 할당량이 부족하면 리소스 선택과 함께 점검합니다.” 저장 HTML은 제품 사설 백엔드와 연결되지 않음을 밝히고 제출 없이 끝낸다. |

### 3차수: 옵션의 실패 사례를 화면에서 이어서 설명

화면에서 GPU와 노드를 고를 때 “단일 노드 코드를 여러 노드로 올려도 자동으로 분산 학습이 되지는 않습니다”라고 설명한다. Shared Memory는 데이터 로더와 프레임워크의 요구량을 확인하는 옵션이며 무조건 크게 쓰는 값이 아니다. 실제 계정의 GPU 할당량과 사용 가능한 리전을 확인해야 한다. 이 저장 화면의 선택지를 현재 모든 계정에서 제공되는 상품 목록으로 확대 해석하지 않는다.

이미지와 Command 영역에서는 원본 demo와 한국어 텍스트 예시를 구별한다. 한국어 예시의 명령은 python /lesson/train_text.py --bundle /bundle --output /output/text다. 이미지가 /lesson/train_text.py를 포함하는지, /bundle이 연결되는지, /output/text가 저장 대상인지 차례로 확인한다. 경로 불일치를 보여 주는 예시는 실제 오류 로그가 아니라 설명용 가정으로 표시한다.

요약 화면에서는 일곱 개 값을 한 번에 읽지 말고 학습 형태·GPU·노드, 이미지·명령, 입력·출력 세 묶음으로 훑는다. 각 묶음에서 하나의 반례를 강사가 바로 제시하고 해결을 말한다. 예: 이미지 접근 불가면 레지스트리 권한, 입력 없음이면 스토리지 연결, 실행 파일 없음이면 이미지와 Command를 수정한다. 생성 버튼은 누르지 않는다.

### 4차수: Spot 선택을 사례에 적용

첫 사례는 시간 제한이 엄격하고 중단 시 결과 제출을 놓치는 작업이다. Spot 비용만 보고 선택하면 대기와 회수 때문에 마감 위험이 생긴다. 둘째는 체크포인트를 자주 저장하고 중단을 감수할 수 있는 장시간 실험이다. 이 경우 Spot이 후보가 될 수 있지만 사용 가능한 GPU 자원, 저장 주기, 재시작 코드가 필요하다. 두 사례에서 가격을 숫자로 비교하지 않는다. 현재 계정 견적과 실제 중단 조건을 확인해야 하기 때문이다.

저장된 Spot 폼의 Job Failover 불가 표시를 읽은 뒤, 공개 문서의 GPU 장애 Failover와 Spot 재개를 별도의 칸에 둔다. “기능 소개에 둘 다 있다고 해서 이 생성 폼에서 동시에 켤 수 있는 것은 아닙니다.” 코드 오류의 예로 존재하지 않는 입력 경로를 보여 준다. 이것은 다른 GPU로 옮겨도 고쳐지지 않는다. 반대로 체크포인트가 있어도 복원 코드가 없으면 이전 단계부터 이어지지 않는다는 반례를 제시한다.

원본 demo의 trainer_state.json은 best_global_step 10과 best_model_checkpoint 경로를 기록한다. optimizer.pt, scheduler.pt, rng_state.pth도 보존돼 있다. 이 파일들이 어떤 진행 상태를 담는지 설명한 뒤 복원 코드를 실제로 실행했다는 기록은 없다고 명시한다. 마지막에 “저장 화면의 Failover 제한”, “공식 Spot 재개 설명”, “체크포인트 존재”, “실계정 복원 조건 미확인”을 네 줄로 정리한다. SageMaker와의 세부 비교는 7차수로 미룬다.

### 6차수: 결과 파일에서 직접 읽을 근거

- 원본 demo의 metrics/baseline.json과 metrics/finetuned.json은 모두 samples: 20, intent_accuracy: 0.05, macro_f1: 0.037037..., json_schema_rate: 0.05다. 학습과 업로드 완료는 확인되지만 이 보존 평가의 성능 개선은 확인되지 않는다. 20개 표본의 smoke run을 일반화 성능의 증거로 쓰지 않는다. 결과의 adapter/adapter_model.safetensors는 LoRA 어댑터이며 입력 기반 모델의 model/model.safetensors와 구별한다.
- 한국어 텍스트의 before.json은 700건, 정확도 0.16, macro-F1 약 0.1268이고 after.json은 700건, 정확도 약 0.8529, macro-F1 약 0.8514다. comparison.json의 accuracy_delta_pp 69.2857...은 69.29%포인트라고 읽는다. validation 이력은 epoch 1의 macro-F1 약 0.8525가 epoch 2의 약 0.8353보다 높다. test 결과와 validation 이력을 같은 분할로 혼동하지 않는다. checkpoint_reload_verified: true는 모델 재로딩 확인이지 Spot 회수 테스트가 아니다.
- 이미지의 before.json은 2,000건에서 정확도 0.112, after.json은 0.862다. comparison.json의 개선 폭은 75.0%포인트, 학습 이력은 4개 epoch다. 결과 파일 model.pt는 이미지 모델이며 텍스트의 model/model.safetensors와 파일 형식과 추론 환경이 다르다. 두 과제는 표본과 레이블이 다르므로 정확도 숫자만으로 우열을 매기지 않는다.
- 마지막으로 세 Job을 실행 완료, 평가 개선, 모델 파일, GPU 시계열 네 열로 비교한다. 원본 demo는 실행 완료와 어댑터 파일이 있으나 보존 평가 개선은 없다. 텍스트와 이미지는 위 표본에서 개선됐다. 가져온 기록의 GPU 시계열은 미보존이라고 쓴다. 이는 AWS G6 실행 결과를 로컬 교육 화면에 가져온 것이며 SCP SAT 실측이 아니다.

### 추가 콘텐츠: 이미지 혼동행렬로 정확도 너머의 오류 찾기

confusion_matrix.json의 열과 행이 어떤 라벨 순서인지 labels_ko를 먼저 확인한다. 각 실제 라벨은 200건이다. 코트 행은 135건을 코트로 맞히지만 32건을 풀오버, 20건을 셔츠로 분류한다. 셔츠 행은 119건만 셔츠로 맞히고 34건을 티셔츠/상의, 20건을 풀오버로 분류한다. 전체 정확도 86.2%만으로는 이 취약한 범주를 발견하기 어렵다. 이 분석은 저장된 혼동행렬에 근거한다. 텍스트 Job에는 동등한 혼동행렬 파일이 보존되지 않았으므로 같은 분석을 했다고 말하지 않는다.

### 7차수: 세 요구사항을 끝까지 판정하는 내레이션

요구 A는 기존 train.py, 자체 컨테이너, 결과 가중치 파일을 유지해야 하는 팀이다. SAT와 SageMaker를 후보로 올린 뒤 SAT의 현재 BYOC 제공 상태, GPU 리전·할당량·스토리지 연결을 확인 항목으로 남긴다. SageMaker에는 IAM과 S3, 네트워크·이미지 레지스트리 설정이 필요하다. Bedrock 파인튜닝은 임의 코드를 그대로 실행하는 선택지가 아니라는 이유로 제외한다.

요구 B는 지원 기반 모델을 지정된 데이터 형식으로 조정하고 Bedrock에서 추론하려는 팀이다. 지원 모델·리전·데이터 형식·맞춤 모델 사용 비용이 맞으면 Bedrock이 후보가 된다. 일반 가중치 파일을 직접 반출해 자체 런타임에서 쓰려는 요구가 추가되면 이 선택을 다시 검토해야 한다. 결과 파일에 접근한다는 말과 서비스가 반출을 보장한다는 말은 다르다.

요구 C는 긴 학습을 중단 가능한 자원으로 실행하려는 팀이다. SAT Spot에서는 저장 폼의 Failover 제한과 공식 기능 소개를 함께 적고 실제 계정 조건을 확인한다. SageMaker Managed Spot에서는 체크포인트를 S3에 저장하고 코드가 복원하도록 구성하며, 최대 대기 한도와 용량 부족 시 On-Demand 자동 전환이 없다는 조건을 적는다. 견적은 GPU 단가뿐 아니라 실패·대기·재시작·스토리지·추론까지 포함해 같은 성공 기준으로 계산한다.

세 사례의 결론을 강사가 화면에 완성한다. 답을 시청자에게 쓰게 하거나 발표를 기다리는 시간을 두지 않는다. SAT Job은 자체 학습 코드 실행에 가깝고 Bedrock은 지원 모델 조정에 가깝다는 서비스 경계를 마지막으로 다시 말한다.

## 녹화 전 확인

- 로컬 Job 목록과 세 Job의 상세·로그·평가·결과 파일, 저장된 On-Demand·Spot 폼을 연다. 생성 버튼은 누르지 않는다.
- 각 장면에서 보여 줄 실제 파일과 값, 출처를 확인한다. GPU 시계열이 없으면 없음으로 표시한다.
- 시범 녹화 후 실제 재생 시간을 측정한다. 20분을 채우지 못하면 검증된 콘텐츠를 보강하거나 차수를 합친다.
