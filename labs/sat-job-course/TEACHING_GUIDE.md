# 강사용 녹화 대본 · SAT Training Job

**20분 × 8편, 총 160분.** 아래 5분 구간은 강사가 실제로 말하며 화면을 조작하는 시간이다. 인용문은 발화 초안이고, 화면 동작은 녹화 중 직접 수행한다. 질문은 시청자 응답을 기다리지 않고 강사가 사례와 답을 이어서 설명한다. 구간별 시간을 리허설로 측정해야 실제 20분 러닝타임을 보장할 수 있다. 임의의 무음·대기 장면을 넣지 않는다.

로컬 사이트는 SCP 화면을 참고한 교육용 구현이다. [원본 demo](http://127.0.0.1:8080/local#jobs/b669419947d55d6991620cdf9bbcaa1f/details), [텍스트 Job](http://127.0.0.1:8080/local#jobs/2dd8760c5b7b55dc8d440c0d18ad2a4e/details), [이미지 Job](http://127.0.0.1:8080/local#jobs/cb0e433e77965ac9ad283d14027ed2df/details)은 보존된 AWS G6 결과다. SAT 자체 실행 결과라고 말하지 않는다. 저장된 생성 폼은 실제 SCP 백엔드에 연결되지 않는다. 화면의 값과 로그는 녹화 직전에 다시 확인한다.

## 녹화 전 준비

1. 로컬 [Job 목록](http://127.0.0.1:8080/local#jobs), [입력 준비](http://127.0.0.1:8080/local#assets), [On-Demand 폼](http://127.0.0.1:8080/reference/job-new.html), [Spot 폼](http://127.0.0.1:8080/reference/job-spot.html)을 미리 열고 화면 배율을 고정한다.
2. 세 Job의 상세·로그·평가 비교·결과 파일 탭을 열어 링크가 정상인지 확인한다. 서버가 내려갔다면 저장소 루트에서 docker compose -f sat-job-local/compose.yaml up -d --build 로 시작한다.
3. 개인정보, 접속 토큰, 실제 계정 ID가 노출되지 않도록 점검한다. 생성·실행 버튼은 누르지 않는다.
4. 각 구간을 실제로 읽고 시연해 시간을 기록한다. 부족하면 해당 주제의 경로·설정·로그 예시를 추가하고, 길면 반복 문장을 줄인다. 최종 편집 파일의 재생 시간은 각각 20:00으로 확인한다.

## 1차수 · SAT 관리형 Training Job의 구조

**목표:** GPU VM 직접 운영과 SAT Job의 책임 범위를 설명한다. AWS 서비스 비교는 8차수로 넘긴다. **자료:** 상품설명회 전사 00:09–03:20, 06:17–07:16.

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | 제목과  흐름도를 표시한다. “학습은 모델 가중치를 갱신하는 코드의 실행입니다. VM에 로그인하면 사용자가 GPU 드라이버와 컨테이너 실행 환경까지 챙깁니다. SAT에서는 실행에 필요한 내용을 Job으로 제출하고 플랫폼이 자원 배치와 실행 흐름을 맡습니다.” 각 화살표를 가리키며 데이터 오류와 자원 오류가 서로 다르다는 사례를 설명한다. |
| 05:00–10:00 | 저장소와 컨테이너를 구분한 도식을 순서대로 강조한다. “원본 파일은 사용자 스토리지에 있고, Job은 지정한 스토리지를 연결해 컨테이너 내부에서 읽습니다. 이미지에는 코드와 런타임이 있고 Command가 시작점을 정합니다. 실행 후 지표와 모델 파일이 출력 위치에 남습니다.” 상품설명회에서 말한 GPU 클러스터 흐름을 화면의 네 단계에 대응시킨다. |
| 10:00–15:00 | 책임 분담 표를 확대한다. “플랫폼이 자원을 마련해도 데이터 형식, 코드의 파일 경로, 라이브러리 호환성은 사용자가 검증해야 합니다. 예를 들어 잘못된 파일 경로는 GPU를 늘려도 고쳐지지 않습니다. 반대로 준비된 코드라도 자원 할당량이 부족하면 실행 시작 자체가 지연될 수 있습니다.” 두 오류의 관찰 지점을 하나씩 짚는다. |
| 15:00–20:00 | 로컬 Job 목록을 열고 이름·상태·생성 시각·상세 링크만 보여 준다. “Job은 실행 요청을 식별하는 단위입니다. 목록의 완료 표시는 코드가 종료됐다는 뜻이고 성능은 뒤에서 별도로 확인합니다. 여기 보이는 것은 AWS G6 결과를 가져온 교육 기록입니다.” 2차수에서 원본 demo의 입력과 출력 경로를 추적한다는 연결로 마친다. |

## 2차수 · 입력·출력 경로 매핑

**목표:** 저장소 원본, 컨테이너 마운트, Command, 결과 위치를 구분한다. 모델 성능과 로그 판독은 다루지 않는다. **자료:** 원본 demo 입력과 출력.

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | [입력 준비](http://127.0.0.1:8080/local#assets)를 열어 파일 종류, 준비 상태, 검증 표시를 차례로 가리킨다. “학습 시작 전에는 데이터와 모델 파일의 존재 및 무결성을 확인합니다. 파일 수가 맞아도 내용이 다르면 기대한 학습이 아닙니다.” 화면의 현재 값을 읽되 녹화 전 확인한 값만 말한다. |
| 05:00–10:00 | [원본 demo 상세](http://127.0.0.1:8080/local#jobs/b669419947d55d6991620cdf9bbcaa1f/details)의 이미지 URL, Command, 마운트 필드를 확대한다. “이미지는 실행 환경, Command는 실행할 프로그램, Mount Path는 프로그램이 입력을 보는 내부 위치입니다. 스토리지의 원래 URI와 내부 디렉터리는 같은 값일 필요가 없습니다.” 화면 값으로  한 줄을 직접 완성한다. |
| 10:00–15:00 | 파일 흐름도에서 입력 파일을 따라 코드가 읽는 위치까지 이동한다. “Command가 를 호출해도 그 파일이 이미지 안에 없다면 시작에 실패합니다. 입력 마운트가 다른 경로면 파일을 찾지 못합니다. 출력 디렉터리를 준비하지 않으면 학습이 끝나도 결과가 기대 위치에 남지 않을 수 있습니다.” 각 실패가 생기는 위치를 커서로 표시한다. |
| 15:00–20:00 | 원본 demo 결과 파일 탭에서 실제 있는 파일과 링크만 보여 준다. 모델 가중치, 지표, 로그의 파일 역할을 구분하고, 없는 파일은 없는 것으로 표시한다. “경로 검증의 끝은 결과 파일이 접근 가능한가입니다. 파일의 성능 해석은 7차수에서 합니다.” 원본 스토리지·내부 입력·명령·출력의 네 칸을 화면으로 다시 연결한다. |

## 3차수 · On-Demand Job 생성 폼

**목표:** 저장된 제품 화면의 필드를 순서대로 검토한다. 생성 버튼은 누르지 않는다.

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | [On-Demand 폼](http://127.0.0.1:8080/reference/job-new.html)을 열어 학습 형태, Job명, 프레임워크, Failover 표시를 순서대로 보여 준다. “On-Demand는 요청한 자원을 사용해 학습하는 구성입니다. Job명은 실행 기록을 식별하기 쉽게 만들고, 프레임워크 선택은 이미지의 실제 런타임과 맞아야 합니다.” 화면에 없는 옵션은 만들어 설명하지 않는다. |
| 05:00–10:00 | 리소스, GPU 수, 노드, Shared Memory 영역을 스크롤하며 보여 준다. “모델 크기와 배치 크기는 메모리 요구량에 영향을 주고, 노드 수는 분산 학습 코드 준비와 연결됩니다. GPU를 여러 개 고른다고 코드가 자동 분산되는 것은 아닙니다.” 로컬 G6/L4 표시는 교육 구현의 고정값이며 SCP 제품 전체 선택 범위가 아님을 명시한다. |
| 10:00–15:00 | 이미지 URL, 레지스트리 인증, Command, Volume/Object Storage 필드를 보여 준다. “이미지 안의 코드 경로, Command, 마운트 위치가 한 세트로 맞아야 합니다. 사설 레지스트리라면 접근 권한도 필요합니다.” 2차수의 원본 demo 경로를 이 폼의 해당 필드에 대응시키되 실제 Job을 제출한 것으로 말하지 않는다. |
| 15:00–20:00 | 요약 영역을 위에서 아래로 읽으며 이름·학습 형태·리소스·이미지·명령·스토리지·출력 위치를 대조한다. “요약은 실행 전에 불일치를 찾는 마지막 화면입니다. 데이터 경로가 틀리면 Command와 함께, GPU 할당량이 부족하면 리소스 선택과 함께 점검합니다.” 저장 HTML은 제품 사설 백엔드와 연결되지 않음을 밝히고 제출 없이 끝낸다. |

## 4차수 · Spot과 복구 조건

**목표:** Spot 자원 회수, GPU 하드웨어 장애, 체크포인트를 구별한다. **자료:** 상품설명회 03:20–05:08, 09:10–10:07과 [공식 근거](SERVICE_COMPARISON.md).

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | [Spot 폼](http://127.0.0.1:8080/reference/job-spot.html)에서 학습 형태와 자원 항목을 보여 준다. “Spot은 유휴 GPU 자원을 활용하므로 시작을 기다리거나 실행 중 회수될 수 있습니다. 과금 사용 시간과 완료까지 걸린 달력 시간은 다릅니다.” 마감이 엄격한 작업과 중단 가능한 실험의 선택 기준을 강사가 두 사례로 해설한다. |
| 05:00–10:00 | 같은 화면의 Job Failover 안내 문구를 확대한다. “이 저장 화면에는 Spot Training에서 Job Failover를 사용할 수 없다고 표시됩니다. 삼성SDS의 공개 설명은 Spot 중단·재개 관리와 GPU 하드웨어 장애 Failover를 별개의 기능으로 소개합니다. 공개 설명만으로 이 화면에서 둘을 동시에 켤 수 있다고 추론하면 안 됩니다.” 화면 문구와 문서의 범위를 분리해 표시한다. |
| 10:00–15:00 | 회수, 하드웨어 장애, 코드 오류를 세 줄 표로 표시한다. “자원 회수는 Spot의 운영 조건이고 GPU 고장은 물리 자원의 실패입니다. 코드·설정 오류는 다른 GPU로 옮겨도 그대로 남습니다. 체크포인트는 학습 상태를 저장하고 코드가 그 상태를 복원해야 진행분을 이어 갈 수 있습니다.” 체크포인트 없이 재시작하면 처음부터 진행할 수 있는 예를 설명한다. |
| 15:00–20:00 | [비교 근거](SERVICE_COMPARISON.md)의 Spot 행과 SageMaker 제약만 짧게 확인한다. “Managed Spot도 체크포인트 코드, 대기시간 제한, Spot 용량을 고려해야 하며 On-Demand로 자동 전환되지는 않습니다. 실제 SAT Spot과 Failover의 동시 적용 조건은 계정·리전에서 확인해야 합니다.” 화면에서 확인한 사실과 미확인 사항을 각각 한 문장으로 마친다. |

## 5차수 · Job 상태와 진단 순서

**목표:** 상태와 관찰 자료의 역할을 연결한다. 4차수의 복구 개념이나 7차수의 정확도 수치를 반복 설명하지 않는다.

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | 준비→대기→실행→종료 상태 흐름도와 로컬 목록의 상태 표시를 보여 준다. “상태는 현재 Job이 어느 단계인지 알려 줍니다. 종료 상태인 Completed는 실행 완료이며 모델의 유용성을 판정하지 않습니다. Failed는 원인을 찾으라는 신호입니다.” 상태별로 먼저 확인할 화면을 표시한다. |
| 05:00–10:00 | 상세·모니터링·로그·평가·결과 파일 탭을 한 번씩 전환한다. “상세는 요청한 설정, 모니터링은 자원 사용, 로그는 실행 사건, 평가는 모델의 측정값, 결과 파일은 남은 산출물입니다.” 같은 ‘성공’ 주장에도 어떤 화면이 근거가 될지 사례별로 연결한다. |
| 10:00–15:00 | 입력 누락, 이미지 접근 오류, Command 오류, 자원 대기 사례를 진단표에 놓는다. “입력 문제는 경로와 파일을, 이미지 문제는 레지스트리 접근을, Command 문제는 이미지 속 코드와 인자를, 자원 대기는 할당량과 상태를 확인합니다.” 로그를 아직 읽지 않고 어디서 근거를 찾을지만 보여 준다. |
| 15:00–20:00 | 가져온 Job의 모니터링 탭을 열어 보존 데이터 범위를 확인한다. “GPU 시계열이 없다면 그래프가 없다고 기록합니다. 로그에 GPU 실행 흔적이 있어도 과거 사용률 그래프를 재구성할 수 있는 것은 아닙니다.” 설정→상태→모니터링/로그→평가→파일 순서를 한 번 시연하며 6차수의 실제 로그 판독으로 이어 간다. |

## 6차수 · 상세와 로그 판독

**목표:** 원본 demo와 한국어 텍스트 Job의 실행 근거를 실제 화면에서 찾는다. 성능 비교는 7차수로 넘긴다.

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | Job 목록에서 원본 demo와 텍스트 Job을 찾아 각각의 상세를 연다. 이름, ID, 상태, 출처를 읽는다. “두 기록이 모두 Completed여도 코드·입력·실행 목적은 다릅니다. 가져온 기록을 로컬에서 방금 실행한 Job으로 설명하지 않습니다.” 두 화면을 나란히 놓는다. |
| 05:00–10:00 | 각 상세의 이미지, Command, 리소스, 입력 위치를 순서대로 비교한다. “같은 상태 표시는 설정의 동일성을 뜻하지 않습니다. 실행 설정을 먼저 확인해야 뒤의 로그 줄이 어떤 프로그램에서 나온 것인지 알 수 있습니다.” 차이점을 화면에 표시한다. |
| 10:00–15:00 | 두 Job의 로그 탭을 차례로 열고 실제 로그에서 시작, 학습 진행, 종료의 근거 줄을 찾는다. 화면 내 검색을 사용해 문구와 순서를 보여 준다. “없는 문구를 예상해 채우지 않고 실제 화면에 남은 줄만 인용합니다.” 길이가 길면 검색 결과 전후 문맥을 함께 보여 준다. |

## 7차수 · 평가와 결과 파일

**목표:** 실제 지표의 의미와 산출물의 재사용 조건을 설명한다. **수치:** 텍스트 test 700건 16.0%→85.29%, 이미지 test 2,000건 11.2%→86.2%. 녹화 전에 화면 값과 대조한다.

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | [텍스트 평가 비교](http://127.0.0.1:8080/local#jobs/2dd8760c5b7b55dc8d440c0d18ad2a4e/comparison)를 연다. test 700건, 학습 전 16.0%, 후 85.29%의 표시와 지표 이름을 가리킨다. “정확도는 이 평가셋에서 맞힌 비율입니다. Completed가 아니라 평가 결과가 성능 근거입니다.” 데이터 분할과 표본 수의 의미를 함께 설명한다. |
| 05:00–10:00 | [이미지 평가 비교](http://127.0.0.1:8080/local#jobs/cb0e433e77965ac9ad283d14027ed2df/comparison)를 열어 test 2,000건, 11.2%→86.2%를 읽는다. 두 과제의 표본 수와 난이도가 다르므로 정확도 숫자만으로 모델의 우열을 단정하지 않는다고 설명한다. 두 결과 모두 AWS G6 Docker 기록임을 화면에서 확인한다. |
| 10:00–15:00 | 각 결과 파일 탭에서 comparison.json, 텍스트 model/model.safetensors, 이미지 model.pt를 찾아 파일 역할을 해설한다. “JSON은 측정 결과, 모델 파일은 가중치입니다. 모델 파일이 있어도 동일한 전처리와 런타임이 없으면 바로 추론할 수 없습니다.” 실제 파일 링크를 열어 접근 가능 여부를 확인한다. |
| 15:00–20:00 | 모니터링 탭의 GPU 시계열 유무를 보여 주고, 결과 파일 접근과 서비스가 제공하는 반출 기능을 분리한다. “가져온 기록에서 시계열이 보존되지 않았다면 없음으로 표기합니다. 모델 이동에는 형식·권한·라이선스·런타임을 확인해야 합니다.” 평가 표본, 전후 지표, 파일 존재, 미보존 자료를 한 화면 표로 정리한다. |

## 8차수 · 실무 서비스 선택

**목표:** 앞선 SAT Job 지식을 [비교표](SERVICE_COMPARISON.md)에 적용한다. 1차수에서 미룬 SageMaker·Bedrock 비교는 여기서 한 번만 자세히 다룬다.

| 영상 시각 | 화면 및 강사 발화 |
|---|---|
| 00:00–05:00 | 세 서비스의 주 용도와 코드 자유도 행을 보여 준다. “기존 train.py와 자체 컨테이너를 실행하려면 SAT와 SageMaker Training Job이 후보입니다. Bedrock 파인튜닝은 지원 기반 모델을 정해진 방식으로 조정하는 서비스입니다.” SAT BYOC는 공개 소개가 있지만 현재 계정·리전 제공 여부 확인이 필요함을 표시한다. |
| 05:00–10:00 | 요구 A ‘기존 PyTorch 코드와 모델 파일 유지’를 화면에 쓰고 SAT와 SageMaker의 스토리지·권한·런타임 조건을 나란히 해설한다. “사용자 스토리지의 파일 접근과 제품 차원의 범용 반출 보장은 서로 다릅니다.” 같은 모델·데이터·성공 기준의 비용 견적이 없으면 가격 우열을 단정하지 않는다고 설명한다. |
| 10:00–15:00 | 요구 B ‘지원 기반 모델 조정 후 Bedrock 추론’을 적용한다. 지원 모델·리전·데이터 형식·맞춤 모델 사용 비용을 확인하고, 임의 train.py 실행 요구가 있으면 후보가 달라지는 이유를 설명한다. 맞춤 모델 저장소와 일반 가중치 파일 반출의 차이도 비교표에서 짚는다. |
| 15:00–20:00 | 요구 C ‘중단 가능한 장시간 학습’을 적용한다. SAT Spot 화면의 Failover 불가 표시와 공식 기능 설명의 범위를 다시 짧게 인용하고, SageMaker Managed Spot의 체크포인트·대기 한도·On-Demand 전환 부재를 검토한다. 화면에 의 완성 예를 보여 준 뒤 결론을 말한다. 시청자 작성·발표 시간은 넣지 않는다. |
